# 声桥 VoiceHub

独立开发的 Mac 实时语音后端。客户端通过 WebSocket 接入，会话、模型和 UI 不依赖
ESP32；附带网页语音客户端和小智协议适配。运行时代码全部位于本目录，不导入旧项目代码。

当前版本为 **0.1 开发预览**。真实本地语音管线和合成语音打断已联调；真实外放 AEC、
ESP32 新服务接入和长时间运行尚未验收，不能据此宣称生产稳定。

## 启动

在这台 Mac 上已有兼容的 Python 运行库，直接运行：

```sh
cd /Users/huzhiwei/ai/miaoban/realtime_backend
./run.sh
```

需要后台常驻（关掉终端也继续跑）时用 `start.sh`：

```sh
./start.sh              # 后台启动；已在运行则复用
./start.sh --status     # 看进程、控制台和设备通道地址
./start.sh --restart    # 先停后启（改了代码/配置后用这个）
./start.sh --stop       # 停止
```

`start.sh` 把 PID 写到 `data/server.pid`、日志追加到 `data/server.log`，
控制台固定 `127.0.0.1:8765`；设备通道是否开启由 `data/connections.json` 里的
`device_enabled`/`device_host`/`device_port` 决定，脚本启动后若发现本机私网地址
和保存的设备地址不一致会给出提示。

打开 <http://127.0.0.1:8765/>，进入“连接实验室”：

1. 点击“连接文字”，输入一句话，检查本地 LLM 和播放。
2. 点击“开启麦克风”，授予浏览器权限，默认手动激活后可连续对话。
3. 说话结束后等待语音回复；支持 AEC 的客户端可在播报期间插话。也可点击“打断回复”。
4. 空闲 30 秒后回到待机；点击“激活聆听”，或使用选定的唤醒机制再次进入对话。
5. 左侧「录音」页集中显示当前录音、实时转写和录音文件；录音时不会回答。

喵伴旧协议客户端在空闲超时后会关闭本轮 WebSocket 连接，由设备恢复待机画面和
本地唤醒词检测。再次喊唤醒词时建立新连接，避免设备留在聆听画面而后台已经待机。

### 录音模式

录音模式与普通对话互斥：进入后把解码后的麦克风音频写入一个 16 kHz 单声道
16-bit WAV，同时按 VAD 停顿切分语音段，在本机做转写并把每段话作为一行实时
推送到网页。它不启动对话轮次，不调用 LLM，也不合成普通回复；适合口述、会议或
现场记录，而不是让助手“边录边答”。

左侧导航有独立的 **「录音」** 页，采用“左边历史、右边详情”的工作台布局：
左侧点一条录音，右侧显示该录音的文字、音频播放器和导出操作。网页聊天页只保留
对话；录音进行时那里会显示进入录音页的提示。

右侧转写支持：

- 点击任意一行，音频跳到该行的起始时间并继续播放
- 拖动播放进度条，当前段落会同步高亮并滚动到可见位置
- “导出文字”下载带时间戳的 txt
- “下载录音”下载 WAV（录音进行中不可用）；“降噪”生成可与原始对比的降噪副本
- “生成会议纪要”用本机 Qwen3.5-4B 按模板生成，可编辑、导出 Markdown/TXT

开始方式：

- 对着已唤醒/已连接的麦克风说“开始录音模式”（也接受“开始录音”“进入录音模式”）。
- 在网页客户端开启麦克风后说“开始录音模式”。「录音」页只负责查看、实时转写、
  停止和下载，不提供启动或麦克风连接入口；以后网页客户端会独立于服务端部署。

停止方式（只有以下明确动作会结束录音）：

- 在「录音」页选中正在录的那条，点“停止并保存”。
- 按喵伴的开关键。设备在聆听时会关闭通道，在播报提示时会发送 abort；两者都会
  让后端保存当前录音。
- 说“停止录音模式”。这是可选的二次确认流程：助手会问一次，只有接下来明确说
  “确认停止”（或再次说“停止录音模式”）才真正结束；20 秒内没有确认就继续录音。
  语音停止和分句转写都需要 Silero VAD 与**本机** ASR；若 ASR 配置为 HTTP 接口，
  录音音频不会被上传做转写/停止检测，实时文字会关闭，录音仍可继续，用网页或
  开关键停止。

转写按“停顿”换行：停顿短于约 1 秒时，不换行，接在上一行末尾并补一个句号；
停顿更长才另起一行。每行带上录音内的相对时间戳（如 `[00:12]`）。网页通过
`recording.transcript` 事件实时显示，时间戳单独排版；重新打开录音时也会从 txt
还原时间戳。停止/确认停止这类控制指令不会写入转写。
文字与音频一起保存在 `data/recordings/`：

- `<id>.wav`：完整原始音频
- `<id>-speech.wav`：只保留 VAD 人声片段的精简音频（如果检测到人声）
- `<id>-ready.wav`：最终精简音频（去空白 + 降噪），播放器和“下载精简音频”使用
- `<id>-speech.json`：完整时间轴到精简时间轴的映射，供文字/证据跳转使用
- `<id>-clean.wav`：完整时长的降噪副本（内部保留，页面不再暴露多个音源）
- `<id>.txt`：逐行转写，UTF-8，每行格式为 `[mm:ss] 文字`
- `<id>.json`：会话、时间、时长、设备等元数据

「录音」页的播放器使用完整音频同步转写，并分别提供“下载完整音频”和
“下载精简音频”。精简音频只有在 VAD 检测到人声时才会生成；没有可用 VAD 时
只保留完整音频。旧录音可以这样补生成精简版（不修改完整音频）：

```sh
cd realtime_backend
python scripts/build_speech_only.py --all
# 或只处理一条：python scripts/build_speech_only.py --id <32-hex-id>
```

### 断线、断电与异常恢复

录音数据不只依赖“正常停止”：

- WAV 和精简 WAV 每 **2 秒**执行一次 `fsync`，避免整机断电时把最近很久的音频留在系统缓存
- 每 **10 秒**更新一次 WAV 头长度，并写一份 `status=active` 的元数据检查点；即使进程被直接杀掉，
  文件头和设备/开始时间也还在
- 每行转写写入后 `fsync`，最后一行不完整时读取会自动丢弃该行而不破坏前面内容
- 网络断开时 WebSocket 关闭会立即触发保存；半开连接（例如设备突然没电但 TCP 还没断）在
  **5 分钟没有收到任何音频包**后自动停止并保存
- 下次启动会扫描遗留 WAV，修复完整、精简、降噪、ready 文件的长度头；已有 active 检查点会
  保留 session/device/started_at，并根据 txt 恢复说话人数量，标记为 `recovered`
- 如果整个进程在写文件过程中被杀，最多可能丢最近约 2 秒音频；已经 `fsync` 的音频和逐行文字
  可以恢复。操作系统/磁盘损坏不在保证范围内

### 刺耳杂音与降噪

部分喵伴录音在近距离/大音量下会削波，并带有明显的 2–8 kHz 高频毛刺；本地实测
同一条 38.6 秒录音 4–6 kHz 能量占比 7.7%，而干净网页录音接近 0，削波样本约
0.15%。这不是持续的宽带底噪，单纯“噪声门”效果有限，因此使用：
`高通 70 Hz → adeclip 削波修复 → 高频搁架衰减 → 低通 → 限幅`。

- 保留原始 `<id>.wav`；播放器默认播放 `<id>-ready.wav`（去空白 + 轻降噪），
  不再让用户选择音源。
- 页面只有两个下载：“下载精简音频”（处理后的版本）和“下载原始音频”。
- 精简音频是剪掉空白后的短时间轴；`<id>-speech.json` 保存完整→精简的映射，
  所以点击文字/证据仍会跳到正确位置。
- 旧录音可用脚本批量补生成；新录音停止后自动具备空白片段和映射，第一次播放
  或下载时生成 ready 文件，不需要用户操作：

```sh
python scripts/build_clean_audio.py --all --profile mild
python scripts/build_clean_audio.py --id <32-hex-id> --profile strong --force
```

- 降噪只能减轻已经削波的失真，不能恢复被削掉的波形；如果刺耳来自外放啸叫、
  多人重叠或设备本身故障，仍需要改善摆放/增益或更换设备。
- 处理过程在后台线程调用本机 ffmpeg，不阻塞 aiohttp；没有 ffmpeg 时返回明确错误。

会议纪要使用本地 Qwen3.5-4B，全部生成和保存都在本机；录音、文字和纪要
都不会进入对话历史，也不会自动上传。断线、服务正常关闭、达到 4 小时上限或写入
失败也会结束并保存；异常重启后，没有元数据的 WAV 会根据文件长度修复头部并标记为
recovered，已有的 txt 会保留。

开始/停止录音模式被视为模式切换，而不是对话轮次：正在进行的回复和播报会被
立即打断，开始后不再生成任何回复；停止保存后回到**待机**，不会继续刚才的对话，
需要再次唤醒才能聊天。停止录音的二次确认提示仍会播报一次；确认停止本身不再播报
“录音已停止”。因此录音开头不再有“开始录音，只录不答”的提示音。

### 发言人区分（匿名）

录音默认尝试区分不同说话人。每个停顿语音段在本机用缓存的
`speechbrain/spkrec-ecapa-voxceleb` 提取声纹向量，在线聚类后给转写行加
`说话人1`、`说话人2` 等标签；左侧历史和右侧详情会显示发言人数量。

- **只保存标签，不保存声纹**：向量只在内存中参与聚类，不写 txt/json，也不上传。
- **不认姓名、不跨录音认人**：每次录音重新编号；想知道“谁”需要额外做声纹注册。
- **阈值可调**：`VOICEHUB_SPEAKER_THRESHOLD`（默认 0.25）、
  `VOICEHUB_SPEAKER_MAX`（默认 6）、`VOICEHUB_SPEAKER_MIN_SECONDS`（默认 1.2）。
  如果两个人被合并，可适当降低阈值；一个人被拆开，可升高阈值。
- **停止时修正**：只有一段的孤立聚类会并入最接近的说话人，减少单句误判。
- **短停顿合并只发生在同一说话人**：换人时即使停顿很短也会另起一行。
- 受远场、回声、重叠说话和短句影响，结果只是近似分组；设备只上传单路混音，
  不能用 4 麦阵列的方向信息做空间分离。
- 如果本机声纹模型缺失或推理失败，转写继续，只少了发言人标签；页面会提示
  `recording.speaker_unavailable`。

### 实时说话人分轨与会后重分析

录音过程中不再只给每个 VAD 长段一个声纹标签：每个 ASR 段会按 1.6 秒窗口
（0.8 秒步进）批量提取声纹，在线聚类后把逐字稿句子分给连续说话人，实时
显示说话人1/2。窗口阈值可用 `VOICEHUB_LIVE_SPEAKER_THRESHOLD` 调整（默认
0.42）。实时结果仍是近似的；停顿超过 20 秒的长会议会在停止后自动做整段
重分析，最终逐字稿以停止后结果为准。

默认会议纪要在会后重分析完成后自动生成一份“通用详细纪要”，不需要手动点。
这一份会消耗本地 Qwen3.5-4B 的额外内存和生成时间；已有同模板纪要时不会重复
生成。


即使实时已按窗口分轨，连续对话/播客仍可能因为远场、重叠和短窗口而不稳定。
停止后会对长录音做一次整段重分析：

```sh
cd realtime_backend
# 等待一条仍在录的录音停止，然后自动重分析
python scripts/rediarize_recording.py --id <32-hex-id> --speakers 2 --wait
```

- 对整段 WAV 做 1.6 秒滑动窗口声纹提取、KMeans 聚类、时间平滑，切成说话人轮次
- 默认 `--mode text`：**保留原逐字稿文字**，按标点切成句子，再按时间把句子归到
  对应说话人；不会因为短轮次 ASR 切断词语而降低文字质量
- `--mode asr` 可选：每个轮次重新调用本机 ASR，适合想重录的情况，但轮次边界
  可能切断词语，默认不使用
- 原始 txt 先保存为 `<id>.txt.before-diarization`，WAV 完全不改
- 结果写入原 txt 和元数据 `speaker_count`，页面刷新即可看到
- 默认 `--speakers 2`；多人圆桌可以试 `--speakers 3` 或 `4`
- 适合播客、访谈、会议回放；句子时间戳是按原行时长和字数比例估算的，播放定位
  可能有几秒偏差，但文字本身保留。此功能目前是本地脚本，尚未接到页面按钮。

### 会议纪要（本地 Qwen3.5-4B）

录音结束、最终 txt 和说话人标签都落盘后，详情页的“生成会议纪要”会调用本机
MLX 模型生成可编辑、可导出的详细纪要，不连接云端。

- 默认模型：`mlx-community/Qwen3.5-4B-MLX-4bit`（本机已缓存的实际模型），可用
  `VOICEHUB_MINUTES_MODEL` 指向另一个本地模型目录或已缓存模型 ID。
- 内置模板：通用详细纪要、项目周会、技术评审、产品需求讨论、客户沟通。界面
  还可以保存自定义模板（名称、关注点、栏目）。
- 生成流程：锁定停止后的最终 txt → 过滤“开始/停止录音模式”等控制语 →
  按约 3800 字分段 → 本地模型每段输出结构化 JSON（议题、关键点、决策、行动项、
  风险、问题）→ 校验每条证据的行号和原文引用 → 去重合并 → 按模板确定性渲染
  Markdown。
- 证据：每条决策/行动项/风险/问题尽量保留 `[mm:ss] 说话人N：「原文」`；新版
  录音的页面上证据是可点击的，会跳到完整音频对应位置。旧录音没有时间戳时显示
  行号且不能跳转。
- 模型每轮只处理一个片段，因此不受语音聊天 `max_tokens=240` 和 worker 2048
  token 限制；纪要生成并发为 1，在独立线程中运行，不阻塞 aiohttp 事件循环。
- 任务状态持久化在 `data/meeting_minutes/jobs/<recording_id>/`，刷新页面不丢；
  服务重启时未完成任务会标记为 `interrupted`，可以重新生成。纪要不会覆盖旧版本，
  同一录音可以换模板生成多份。
- 支持编辑 Markdown、导出 Markdown/TXT、删除单份纪要；删除录音会一并删除该录音
  的所有纪要和任务。删除录音的路径不会删除其他录音的数据。
- 纪要、转写、证据引用全部留在本机；模型不可用、没有转写、录音还在进行时会返回
  明确中文错误，不会生成空白成功结果。生成内容只通过 `textContent`/受控结构渲染，
  不作为 HTML 注入。
- 实测：4 行转写约 22 秒，11 行约 33 秒（Qwen3.5-4B-MLX-4bit，本机 CPU/MLX）；
  **30–120 分钟长会议尚未实测**，长会按分段数线性增加耗时。
- 当前未做：会后全量重转录/覆盖率补全、DOCX 导出、真实多人会议质量基准和自定义
  模板的编辑/删除界面（API 已支持）。

### 本地 Qwen3-TTS（MLX）

本机可使用已缓存的 `mlx-community/Qwen3-TTS-12Hz-0.6B-CustomVoice-8bit`：

```sh
python scripts/start_qwen_tts.py
```

该脚本启动或复用127.0.0.1:8767服务，离线加载模型并预热，保持单独的常驻MLX工作线程。
后台「模型配置 → 语音合成」选择兼容HTTP API，模型ID填上述模型，API Base URL填
`http://127.0.0.1:8767/v1`，音色`Serena`，PCM采样率`24000`。
无需真实API密钥，密钥环境变量字段可保留`VOICE_TTS_KEY`。
保存后新连接使用配置。诊断目录中的`start_device_listener.py`也会在选择本地Qwen时
先确保此服务启动，再启动后台。

服务仅开放本机健康检查和受限的PCM合成接口，限制为该模型及其预设音色，最多2个
在途请求；客户端断开会取消生成。模型与网络服务分开运行，避免TTS排在同一GPU工作
队列的LLM之后而互相等待。日志为`data/qwen-tts.log`，不保存合成文本或音频。
每句首块生成慢于播放所需速度时，本句会先合成完再发送，避免已知慢启动导致句内
断续；快于实时则直接流式输出。缓存仍受30秒音频上限约束。日志`tts.delivery`中的
`sentence`表示整句缓存、`stream`表示流式；这不能保证推理中途突然加重GPU负载时
永不出现延迟，应结合当次真实负载和包间隔检查。
接口文档：POST `/v1/audio/speech`，JSON含`model,input,voice,response_format:"pcm"`，
返回24kHz单声道s16le流；GET `/health`返回预热状态、模型、音色列表和采样率。

生图和其他本地模型会争用GPU；测首包延迟和生成速度时应记录负载。不要把高负载下
的慢速结果当作该模型的固定性能，也不能将空闲测速视为繁忙时的保证。

启动脚本优先使用 `VOICEHUB_PYTHON`，其次本目录 `.venv`，然后这台机器已有的模型
运行环境，最后系统 Python。新环境安装：

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-local.txt
brew install ffmpeg
./run.sh
```

仅用 HTTP 模型服务时安装 `requirements.txt` 即可。MLX 需要 Apple Silicon 和可访问
Metal 的桌面运行环境。默认 TTS 为 macOS 自带的 Tingting，不需要加载 TTS 神经模型。
使用 `say -v '?'` 查看已安装音色。首次推理会懒加载 ASR/LLM，耗时明显高于热启动。

## 模型与配置

在“模型与语音”分别配置：

| 模块 | 本地支持 | HTTP 兼容接口 |
|---|---|---|
| ASR | MLX Audio Qwen3-ASR | `POST {base}/audio/transcriptions`，multipart WAV，返回 `text` |
| LLM | MLX LM 聊天模型 | `POST {base}/chat/completions`，SSE `choices[].delta.content` |
| TTS | macOS `say` | `POST {base}/audio/speech`，`response_format=pcm` |

Base URL 应包含服务要求的 `/v1`，不要填写具体方法路径。HTTP TTS 必须返回
**单声道、16bit little-endian 裸 PCM**，采样率在配置里填写，服务端会连续重采样为 16k。
不把 WAV、MP3 或供应商私有格式当作 PCM 播放。具体供应商仍需逐家联调；兼容协议测试
不等于已测试所有云厂商。端到端语音模型和已有 Grok Bot 会话未在此版实现。

必要参数缺失时先追问，不调用 MCP。模型暂时不可用会明确反馈，不静默切到云端。
详细契约见 [决策、参数与 MCP](docs/SPEC-rex-mcp-parameters.md)。

- 天气：通过 Open-Meteo 查询当前天气及未来三天预报。未提供城市且未配置默认城市时，
  助手应先询问。返回匹配城市、时区和日期，遇到同名地点应核对。
- 新闻：读取选定 RSS 源的最新条目，可按关键词筛选；默认 BBC World，英文内容由
  LLM 用中文摘要。中新网中文源可选；不同网络下可用性不同。不是全网新闻搜索，
  源不可达时明确报告失败，不擅自换源。新闻发布时间与抓取时间分别保留。
- 系统信息：只读取运行后端的电脑 CPU、内存、磁盘和开机时长，不读取进程、文件或账号。
  支持 `sections:["cpu","memory","disk","uptime"]` 的子集；省略时返回全部概况。
- 本地音乐：在网页上设置后端电脑上的音乐目录并启用。可搜索、播放、暂停、继续、停止；
  支持 MP3/WAV/M4A/AAC/AIFF/FLAC，具体解码由 macOS afplay 决定。多首匹配时返回候选。
  音频输出到后端电脑，不代表已向机器人传输音乐流。扫描最多 5000 首，拒绝目录外符号链接。
- 机器人音量：直接控制猫头扬声器（0–100）。说“音量调到 30”“声音大一点”“静音”
  “现在音量多少”即可。与其它工具不同，它不在工具子进程里执行，而是通过设备的
  MCP 通道（`self.audio_speaker.set_volume`、`self.get_device_status`）直接改设备音量；
  需要设备在线，未连接时会明确说明。静音会记住之前的音量，取消静音时恢复。

示例：“上海明天天气怎么样？”“读三条最新新闻。”“这台电脑内存用了多少？”“把音量调到 40。”

耗时工具前先合成并发送“我查一下，请稍等”一类提示，按音频时钟等待这段音频排空后
才启动工具。客户端仍需正确播放服务端音频；这不等于对物理扬声器做了完成测量。
成功后播报结果；失败或超时有中文语音反馈。事件日志提供 `tool.started`、
`tool.completed`、`tool.failed` 和耗时。打断会取消该轮工具子进程，不输出旧结果。

工具通过独立进程 `python -m voicehub.common_tools` 提供标准 stdio MCP：初始化、
能力协商、工具发现和调用。除内置服务外支持用户导入 stdio 服务；尚未实现 Streamable HTTP 或智能家居。

每个工具独立放在 `voicehub/mcp_tools/` 下：`weather.py`、`news.py`、`system_info.py`、`music.py`。
各文件包含参数 Schema、提示语和统一的异步 `execute(http, **arguments)` 实现；
`mcp_tools/__init__.py` 显式注册工具，`shared.py` 提供有大小限制的 HTTP 读取和时间戳。
`common_tools.py` 只处理 MCP 协议、分发、超时和统一错误；`tools.py` 从注册表生成目录并校验参数。
扩展时新增工具模块、注册并补充边界测试；Rex 还需补充标签、实体字段和训练数据。

“对话模型规划”通过受限 JSON 计划选择工具，不要求 HTTP 服务提供原生 function calling，

禁用所有内置和用户扩展工具后恢复原有对话链路（明确日历问题仍由本机时钟回答）。

[Open-Meteo](https://open-meteo.com/en/docs)。本轮验收见 [MCP 验证记录](docs/MCP-VALIDATION.md)。

**新连接**生效，现有会话的配置快照不变；请重新连接客户端。

## 人声检测与唤醒

检测使用 Silero ONNX（CPU），支持常见 `state/sr` 接口及 faster-whisper v6 的 `h/c` 接口。
可在 UI 填写模型文件路径，也可设置 `VOICE_VAD_MODEL`。留空时查找已安装的
faster-whisper 资产及本机 uv 缓存；没有模型时文字仍可用，语音会明确报告不可用。
UI 的“可用”表示找到了文件，不代表该路径下任意模型均已通过推理验证。

| 唤醒模式 | 行为与限制 |
|---|---|
| device | 设备自己检测唤醒，发送 `wake` / `session.activate`；词表在设备配置 |
| backend | 客户端持续上传，VAD 分句后 ASR 检测唤醒词，可接同句话中的提问 |
| manual | 用户按钮或触摸激活；浏览器实验室默认采用该模式 |

后端唤醒目前是**分句转写检测**，并非低延迟专用关键词引擎。未命中唤醒词的待机
转写不写入对话或事件记录；如果使用 HTTP ASR，转写所需音频仍会送往你配置的服务。
切换到后端唤醒要求客户端声明并真正支持 `continuous_audio`。普通设备不能仅靠服务端
开关就变成待机持续上传。

自然插话要求客户端在播报时仍上传经过 AEC 的音频，并声明 `echo_cancellation=true`。
服务器以连续人声概率确认起声，立刻取消旧轮次并发出 `playback.clear`；客户端必须
停止正在播放的源并清空缓冲。仅发送停止标记而不清除音频队列不算完成打断。
浏览器的 AEC 声明仅说明启用了浏览器约束，实际抗回声效果仍需外放测试。

## 连接其他设备

默认只监听本机。机器人接入时，仅在指定私网 IP 开放设备通道，管理界面继续保留在 127.0.0.1:8765：

```sh
./run.sh --device-host 192.168.2.122 --device-port 8766
./run.sh --print-device-token
```

在受信任局域网通过设备令牌连接；公网部署必须增加 HTTPS/WSS 终止，不直接暴露明文
端口。令牌不放在通用 WebSocket URL 查询参数中，使用 Bearer Header 或首帧 `token`。

Mac 本地管理可直接访问；设备专用监听不提供任何管理 API 或静态页面，强制验证设备令牌；不要将控制监听改为
0.0.0.0。需要远程管理时另行明确配置与授权，当前仍仅允许本机访问。管理员令牌查询：

```sh
./run.sh --print-admin-token
```

手机浏览器麦克风需要 HTTPS（手机访问 Mac 的 HTTP 局域网地址不等于 localhost）。

## 数据和诊断

默认 `data/`（权限 0700），可用 `--data /path` 指定：

- `settings.json`：原子替换写入的配置快照。
- `auth.json`：0600 权限的管理/设备令牌，不进入源码。
- `history.sqlite3`：SQLite WAL，消息、状态、错误与耗时。默认保留 30 天，启动及每小时清理。

不保存原始麦克风/播放音频；保留被打断回复并标记 interrupted。`generated` 只代表生成，
`played` 表示客户端发来匹配播放回执，不代表服务端测量到了物理扬声器声音。
本地数据库未做额外磁盘加密，访问控制依赖 macOS 用户及目录权限。

每连接入站队列最多 64 包，最多 100 音频包/秒，过载明确断开；最多 8 个在线会话。
音频输出按实际时长发送。网页客户端同时限制上传积压与播放积压，断线恢复身份和历史，
不重播旧音频，不自动重发上一条用户消息。
