# 网页麦克风与 AirPods

在「连接实验室」的「输入麦克风」选择实际设备，再点击「开启麦克风」。播放设备和输入设备可能不同，能听见 TTS 并不能证明耳机麦克风已被选中。

页面显示实际采集轨道名称、音量、音频环境采样率、采集帧数和已上传帧数。AirPods 在本机 Chrome 验证中使用 24000 Hz，客户端转换为协议要求的 16000 Hz 单声道 PCM；每帧 40 ms。浏览器先打开输入设备，再按原生采样率构建音频环境，避免在蓝牙路由切换前固定为 16 kHz。

- 输入接近静音：检查选择的设备、麦克风权限和耳机佩戴。保持安静时出现此提示是正常的。
- 没有采集到音频帧或音频暂停：点击「开启麦克风」重建采集链路。
- 采集帧数增长但上传帧数不增长：检查连接状态。WebSocket 握手完成前不会上传。
- 选择其他输入设备时会重新连接，释放之前的麦克风和音频环境。
- 修改客户端唤醒方式也会重新连接，让新模式生效。「手动激活」模式可以点击「激活聆听」从待机恢复。

诊断只显示计数和音量，不保存或额外上传麦克风录音。语音仍只通过原来的 VoiceHub WebSocket 对话链路发送。

## 验证

在 `realtime_backend` 目录执行：

```
node --test tests/test_browser_audio.cjs
python -m unittest discover -s tests -q
```

前端测试覆盖输入设备与音频环境的初始化顺序、失败时释放麦克风、8 / 16 / 24 / 44.1 / 48 kHz 输入的 16 kHz PCM 帧长度与音量统计。实际耳机验证需在浏览器选择 AirPods，并检查后台出现 `speech.started`、`transcript.final` 及回复事件。

## 网页服务端唤醒

选择「后端唤醒」，选择输入麦克风并点击「开启麦克风」。在「待机」时连续说「小宝同学，你好」，说完停顿等待检测和转写完成。测试语音唤醒时不要点「激活聆听」，该按钮会直接激活并绕过唤醒词检查。当前唤醒词显示在客户端提示里。

只说唤醒词会切换到「聆听中」，不会立即播放回复。未匹配时页面显示识别到的文字，以便判断是否存在同音字、漏字或收音问题；这些待机识别反馈不保存到历史或日志。识别匹配完整文字，不进行同音字猜测。
