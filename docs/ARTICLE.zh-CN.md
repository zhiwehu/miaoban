# 我把喵伴的“大脑”搬进了 Mac：ESP32、本地 ASR / LLM / TTS 与听声转头实践

> 技术实践草稿 · 2026-10-24  
> 配套项目暂名：miaoban-voicehub（声桥）。本文记录当前实现与实机调试，不把设计目标当作已完成能力。

我手上有一只喵伴机器人。它有一颗会显示眼睛、能听见声音的猫头，也有一个能带着猫头转动的底座。我想让它使用自己 Mac 上的模型：喊一声“小宝同学”，它能听懂我的话、生成回答，再用我选的声音说出来。

除了聊天，我还希望它有一点“在场感”：有人在旁边说话时，它能判断声源方向，转头朝向说话的人。

做下来，我发现最花时间的地方，是让设备、后端、模型和电机控制之间的状态保持一致。后台已经生成了文字，机器人仍可能完全无声；麦克风能正常识别语音，转头却可能被底座故障保护挡住。每一层都显示“正常”，也不代表整条链路真的工作了。

这篇文章把我的硬件分工、软件实现，以及几个很有代表性的坑整理出来。开发和联调中我使用了 Codex 协助，但每项硬件能力仍然要靠代码、日志和实机反馈核实。

## 一、先把系统分工讲清楚

我的实现分成三部分：猫头、Mac 后端、旋转底座。

| 部分 | 在这台设备上承担的工作 |
|---|---|
| ESP32-S3 猫头 | 双麦采音、设备端唤醒、Opus 音频传输、扬声器播放、屏幕显示、声源方向估计 |
| Mac | 语音分段、ASR 转写、LLM 回答、TTS 合成、会话管理、历史记录和网页控制台 |
| ESP32-C3 底座 | 读取角度反馈、执行有限范围的转动、回报位置和故障、处理堵转与超时保护 |

我的 Mac 是 M4 Max，128GB 统一内存。这是文章中的测试环境，不是项目的最低硬件要求；其他芯片、内存和同时运行的任务都会改变延迟。

![系统架构示意](../media/architecture.png)

猫头与 Mac 通过局域网 WebSocket 连接。Mac 的管理界面只监听回环地址；给设备使用的入口单独监听指定的局域网网卡，并要求设备令牌。这样手机或其他终端以后可以复用会话后端，而不需要把“设备”写死成某一款 ESP32。

声源定位和电机控制走设备本地路径：猫头估计方向，通过 UART 给底座发送有限幅度的转动请求，底座再回报状态。LLM 不直接决定电机该转多少度。

## 二、我用的三套本地模型

当前配置如下：

| 环节 | 实际使用的模型 | 执行方式 |
|---|---|---|
| ASR | `mlx-community/Qwen3-ASR-0.6B-8bit` | Mac 上的 MLX Audio |
| LLM | `mlx-community/Qwen3-4B-Instruct-2507-4bit` | Mac 上的 MLX LM |
| TTS | `mlx-community/Qwen3-TTS-12Hz-0.6B-CustomVoice-8bit` | 单独常驻的 MLX Audio 服务 |
| 音色 | Serena | Qwen CustomVoice 的中文预设音色 |

三套模型的官方说明分别见 [Qwen3-ASR](https://huggingface.co/Qwen/Qwen3-ASR-0.6B)、[Qwen3-4B-Instruct](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507) 和 [Qwen3-TTS CustomVoice](https://huggingface.co/Qwen/Qwen3-TTS-12Hz-0.6B-CustomVoice)。Apple Silicon 推理适配来自 [MLX Audio](https://github.com/Blaizzy/mlx-audio) 与 [MLX LM](https://github.com/ml-explore/mlx-lm)。

一开始，我用 macOS 自带的 Tingting 语音验证完整链路。系统语音让前期联调少了一个神经模型变量。等识别、回答、音频格式和设备播放都能串起来后，再把 TTS 换成 Qwen。

对话推理在本地完成，正常对话不需要把语音发给云端模型。不过，“本地推理”和“整台设备永不访问互联网”是两件需要分别验证的事：模型首次下载、固件版本发现和 OTA 地址仍然要显式配置。我的运行适配器只读取已缓存模型，设备 OTA 也指向本地后端。

## 三、一句话怎样经过这条链路

用户说话后，猫头采集麦克风音频，编码成 Opus 发给 Mac。设备连接使用 16kHz、单声道、60ms 的 Opus 帧；Mac 端将收到的音频解码为 PCM。

后端先做 VAD，也就是判断当前是不是人声、用户是否已经说完。它保留起声前的一小段音频，避免开头的字被截掉，再把分好的这一句话交给 ASR。

这里需要准确说明：当前 ASR 主要处理已经分段的音频，并没有实现逐字输出的流式转写。“实时对话”指的是持续连接、自动接话和增量生成/播放构成的交互体验，不能直接等同于完整的全双工语音模型。

ASR 得到文字后，后端取出当前会话的历史，让 LLM 生成回答。LLM 的增量文本按句子边界或长度拆开，交给 TTS。TTS 生成的声音随后转换成设备需要的格式，再发回猫头播放。

```text
双麦采音 → Opus / WebSocket → VAD 分句 → 本地 ASR
                                     ↓
                              会话历史 → 本地 LLM
                                     ↓
                         分句 → 本地 TTS → 重采样
                                     ↓
                          Opus / WebSocket → 扬声器
```

我把模型接口分别抽出来。ASR、LLM、TTS 都可以换成兼容的 HTTP 服务；这次运行选择的是本地模型。HTTP 兼容只代表接口契约，不能据此认为所有厂商都已经联调通过。

## 四、音频格式必须在边界上统一

Qwen TTS 返回 24kHz 的单声道音频，猫头的网络协议使用 16kHz。我在服务端做连续重采样，再编码成 Opus。

连续重采样很重要。一个 HTTP 数据块不一定恰好对应完整的采样边界，也不应该每来一块就新建一次重采样器。我的处理方式是保留当前轮次的重采样状态，并暂存不足一个 16bit 采样的字节。

HTTP TTS 入口约定返回单声道、16bit little-endian 裸 PCM。WAV、MP3 或带头部的音频文件不能直接当 PCM 送进扬声器。切换模型时，我先验证采样率、字节对齐、非静音波形和音频时长，再接到设备上。

独立的 Qwen 服务只绑定本机回环地址，模型常驻内存。它与 ASR / LLM 的工作队列分开，避免一句回答尚未生成完，TTS 又排在同一个模型线程后面互相等待。进程分开也不代表 GPU 算力分开：它们依然共享同一颗 Apple Silicon GPU。

## 五、我为什么还做了一个 Mac 控制台

只有串口日志，很难判断一次无声究竟发生在哪一层。因此我做了一个本地网页控制台，用来查看已识别文字、回答、连接状态、轮次耗时和错误，也可以分别修改 ASR、LLM、TTS 配置。

后端区分设备、会话、连接与轮次。每轮回答有自己的 `turn_id`，取消旧轮次后，迟到的文本或音频不能继续流入新轮次。WebSocket 连接也不被当作永久的会话身份。

对话记录保存在本机 SQLite 中。音频块不写进事件日志，令牌也不应进入日志。历史中的“已生成”只说明模型完成了输出；没有设备播放确认，就不能把它显示为“用户已经听到”。

这条区分帮我避免了一个常见误判：当控制台上已经出现回答时，我一开始容易认为模型链路没有问题，剩下只是喇叭音量。后来设备计数证明，一部分无声轮次的回复根本没有完整进入播放流程。

## 六、最典型的坑：安静十五秒，下一句只有文字没有声音

这个问题很容易让人怀疑“音频模型是不是自动退出了”。现象是：连续聊天时能听见声音，安静十几秒后再说话，后台仍然能识别和生成，但猫头没有声音；再说一句，有时又恢复。

我没有继续增加音量或反复换模型，而是读了固件的电源管理路径。设备会在 15 秒没有播放后关闭音频输出，这个时间点与现象吻合。

原来的播放流程在重新开启输出时，还沿用上次播放的活动时间。电源定时器与开启流程之间存在竞争风险：新打开的输出可能被旧的超时判断再次关闭。另外，猫头收到“开始播放”只是把状态切换排进主任务，并不代表已经重置了解码器、准备好接收音频。

我做了两层修正：

1. 开启音频输出之前先刷新活动时间；输出开启和定时关闭使用同一把锁。
2. 加入播放准备握手。猫头完成 Speaking 状态切换、解码器重置和输出恢复后，回传本轮 `tts.ready`；后台核对轮次、设备状态和输出开关，再发送音频。

未准备好时，后台会给出明确错误，不能继续把这轮回复当成正常送达。旧固件没有声明这项能力时，后端仍保留兼容路径。

设备还会回传收包、状态丢包、解码和播放计数。一次复听中，两轮回复分别增加了 40 和 70 个收包，解码、播放计数相应增长，状态丢包为 0，用户也听到了声音。这样的证据比“控制台有文字”强得多，但设备写入播放任务仍不等于独立麦克风测量了扬声器输出。

这次修复后，实机复听通过。它说明这条路径值得保留，不代表已经完成所有负载、所有休眠周期的长期可靠性验证。

## 七、另一个状态坑：猫头还在聆听，后台已经待机

小宝有几个很直观的画面：只显示眼睛的待机、眼睛上方竖条变化的聆听，以及显示文字的对话画面。画面可以帮助使用者理解状态，但开发时仍要看实际状态机。

我遇到过一种情况：长时间没有说话后，猫头还保持聆听画面。直接和它说话不理，再喊“小宝同学”也无法唤醒。

原因是后台默认在空闲 30 秒后进入 standby，却没有把这次状态变化同步到旧协议设备。猫头留在 Listening，关闭了本地唤醒词检测；后台又会丢弃设备模式下 standby 时上传的音频，两端一起进入了尴尬的状态。

旧协议没有统一的 standby 指令，我选择在超时后关闭当前对话连接。猫头使用已有的断线回调回到 Idle，恢复本地唤醒。下次唤醒再建立连接。原生网页客户端理解 standby 事件，则可以保持连接。

唤醒词检测、语音对话和连接存活是三件不同的事，必须一起设计状态转换。

## 八、卡顿和电杂音，要把“声音”和“发送节奏”分开查

调试中我还听到过沙沙声、电杂音和明显卡顿。它们不能统一归因为 TTS 音质不好。

一处问题出在发送时钟：如果每块发送完成后再等待该块的音频时长，编码、网络发送和调度开销就会不断叠加。测试里，800ms 音频能被拖到约 1.17 秒。

我改成按照累计采样数维护固定播放时钟，并保留少量发送提前量。合成与发送之间使用有界队列，当前句还在播放时就可以准备下一句。结束时先刷新 Opus 尾包，再给设备缓冲留出排空时间。

原实现中 40ms PCM 块与 60ms Opus 帧也会形成不均匀的出包间隔。单靠平均带宽充足，不能保证扬声器永远有下一帧可播。

编码方面，我对比过同一段合成语音的 Opus 编码再解码结果，最后使用 64kbps、audio 模式。这个比较改善了数字压缩保真度，但不能拿波形信噪比直接证明所有电杂音都来自编码。最终仍要依靠设备复听。

还有一个小插曲：LLM 喜欢在结尾加笑脸，macOS 语音会把 emoji 的名称读出来。于是机器人会在正常回答后追加类似“脸颊泛红的笑脸”的描述。我把 emoji 过滤放在 TTS 输入边界，并在提示词中要求只输出适合朗读的正文，解决了这类后缀。

## 九、Qwen 很小，也会被其他 GPU 任务拖慢

在 M4 Max 上，0.6B 模型并不意味着任何时候都有固定延迟。我同时运行过本地生图和其他 LLM，TTS 的耗时随负载明显变化。

| 单句合成观测 | 音频时长 | 生成耗时 | 说明 |
|---|---:|---:|---|
| 一次较低负载测试 | 3.36 秒 | 2.05 秒 | 首包约 0.52 秒，快于实时播放 |
| 一次较高负载测试 | 3.36 秒 | 约 10 秒 | 直接边生成边播放会断粮 |

这些是单次观测，不是严格隔离变量后的基准，也不是接话总延迟。接话还包括用户说完后的 VAD 等待、ASR、LLM、播放准备和缓冲。

我保留了流式合成，但加入保守的降级：如果一句话的第一块生成速度已经慢于播放所需，就先完成这句话再发送。空闲时继续流式，繁忙时多等一会儿，减少明知供给不足还逐块播出的断续。中途突然增加 GPU 负载，仍可能影响后续输出，这个策略不能替代真正的资源调度。

最后一次完整链路测试中，约 4.5 秒音频经过 Opus 和 WebSocket 发送，模拟接收缓冲没有出现断粮。用户试听新音色后反馈“还可以”。这里我会写“当前可用”，不会写成“所有 Mac 都是毫秒级实时”。

## 十、听声转头怎样工作

转头使用的是双麦原始音频，经 [Espressif ESP-SR](https://github.com/espressif/esp-sr) 的 DOA 模块估计声源方向。

一个需要提前解决的问题是麦克风的所有权。不能让唤醒、ASR 和声源定位各自去读 I2S，它们会争抢采样。我让音频输入任务负责唯一的硬件读取，方向估计通过 observer 取得同一批原始双通道 PCM，再放进有时间戳和序号的有界队列。

方向路径使用人声检测、环境噪声估计和连续方向证据，避免风声或偶发响动直接触发电机。当前灵敏度调整包括把噪声倍率从 2 降到 1.5，把最低 RMS 门槛降到 30，并使用 9 个稳定方向帧、允许短暂无声间隙。

DOA 方向也不能直接当电机的绝对目标角。双麦的正前方参考与底座传感器的中心值不属于同一个坐标系。我先减去标定的正前方角，得到相对偏差，再结合底座真实回报的位置计算目标。

例如，假定正前方参考是 90°，DOA 得到 115°，就先得到约 25°的相对偏差。之后还要经过方向符号、增益、单次幅度和目标范围限制。这些数值是当前设备的标定和控制参数，不能不经测量就推广为其他麦克风间距或电机的物理角度。

底座通过 ADC 角度反馈和受限控制执行转动。软件目标范围、单次命令限幅、稳定时间、冷却时间、传感器故障、堵转和超时保护都保留着。猫头自己播报时暂停跟随，避免追着自己的扬声器转。

我确实遇到过“刷完固件，怎么又不转了”。当时检查发现灵敏度逻辑和开关都还在，底座却持续回报 STALL 故障 2。检查周围是否受阻、重新上电后，故障回到 0，用户也确认转头恢复。不能把这种情况简单归为算法失效，更不能用软件反复清除堵转保护来掩盖问题。

需要留一个明确边界：当前待机听声转头已经有实机反馈；“唤醒后聆听时不跟随”的现象还需要继续单独排查。因此我还不能宣称待机、聆听、播报切换后的所有跟随场景都已验收。

## 十一、现在完成到哪一步

当前可以确认的是：设备能接入本地后端，语音识别、LLM 回答和 Qwen TTS 能完成实机对话；网页能查看历史、日志并修改模型；转头路径已经运行，并有故障回传和运动保护。后端已有 49 项自动化测试，另有 9 个独立的 C++ 控制逻辑测试。

自然插话仍然是后续工作。会话核心已经有取消旧轮次、清空待播和丢弃迟到结果的机制，但真实 ESP32 外放场景的 AEC 没有完成验收。目前不能把“协议能双向传音频”写成“机器人说话时随时开口都能自然打断”。

长时间稳定运行、多设备实际体验、不同硬件的声源标定，也都需要更多记录。后端留出了通用 WebSocket 接口，不代表手机 App 或所有其他设备已经完成适配。

## 十二、代码怎样整理成一个公开项目

我的开源整理分成三个层次：

- 独立的 Python 后端、网页控制台、测试和模型接口。
- 底座控制器及可在电脑上运行的控制逻辑测试。
- EchoEar 猫头完整源码工程、ESP-IDF 构建配置和依赖锁，保留上游版权声明。

猫头适配基于 [xiaozhi-echoear-taibai](https://gitee.com/liunix61/xiaozhi-echoear-taibai)，也依赖小智及 Espressif 的生态，不能写成我从零实现了整个 ESP32 固件。本地固件目录没有 Git 历史，所以我将它整理为源码快照，公开当前使用的核心代码与 EchoEar 板级实现，并用文件哈希记录内容，不虚构它与某个上游提交之间的精确补丁关系。构建依赖由 ESP-IDF 组件管理器提供；提示音使用固定上游提交及校验和另行下载。

公开包不包括模型权重、整机 Flash 备份、NVS、Wi-Fi 信息、设备令牌、真实对话数据库和运行日志。第三方表情、字体、语音资源也没有混进源码包。

代码与模型分别遵守各自许可证。采用 MIT 发布本项目的原创代码；上游固件保留原有 MIT 版权说明，模型由使用者从对应仓库下载并核对许可。项目地址：[zhiwehu/miaoban](https://github.com/zhiwehu/miaoban)。具体安装与构建步骤见仓库 README 和 firmware/README.md。

这次实践最有价值的收获，是建立一条能观察、能解释、能逐步验证的链路。它能识别一句话、说出一句回答，也能告诉我：这一轮声音究竟有没有到达设备，转头为什么被禁止，以及下一次该检查哪一层。
